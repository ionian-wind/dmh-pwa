# Module Import and Export

## Purpose

Move a module (book + its document notes) between installations or generate it
offline from Markdown. The canonical format is a ZIP archive.

## Key files

| File | Role |
| --- | --- |
| `src/utils/moduleImportExport.ts` | ZIP parsing, validation, import |
| `src/views/HomeView.vue` | Import/export/backup entry points |
| `src/modules/ModulesView.vue` | Import with validation modal (button commented out) |
| `src/modules/ModuleView.vue` | Export |
| `src/components/ImportValidationModal.vue` | Validation result UI |
| `scripts/markdown-to-json.js` | Offline Markdown → module ZIP generator |

## Archive format

```
<module-name>_module.zip
├── module.json      # Module record, includes noteTree
├── tree.json        # Duplicate of module.noteTree
├── summary.json     # Human-readable statistics (ignored on import)
└── notes/
    ├── <note-id>.json
    └── ...
```

### `module.json`

Produced by export:

```json
{
  "id": "<original module id>",
  "name": "…",
  "createdAt": 0,
  "updatedAt": 0,
  "noteTree": [ { "noteId": "…", "children": [] } ]
}
```

Produced by the Markdown script: same shape, but with a freshly generated ID
and `children` arrays.

### Note files

Exported notes include:
`id`, `title`, `content`, `typeId`, `tags`, `moduleId`, `createdAt`,
`updatedAt`, `hidden`.

Notes generated by the script include `hidden: true`.

### `summary.json`

Created by both export and script: `moduleName`, `moduleId`,
`totalSections`, `totalNotes`, `generatedAt`. Import ignores it.

## Parsing (`parseModuleZip`)

1. Loads the ZIP with JSZip.
2. Requires `module.json`, `tree.json`, and a `notes/` folder.
3. Parses JSON; invalid module/tree JSON throws, invalid individual note files
   are skipped with a warning.
4. Returns `{ module, tree, notes }` as untyped `any` values.

There is no schema validation, size limit, or content sanitization. Any JSON
shape that the later write accepts can enter the database.

## Validation (`validateModuleImport`)

Given the module record, the tree, and the notes:

- `missingNoteIds` — IDs present in `tree.json` but absent from `notes/`.
- `orphanedNoteFiles` — note files not referenced anywhere in the tree.
- `treeMatchesModule` — sorted ID sets of `tree.json` and
  `module.noteTree` are equal.

The validation modal disables import when the tree does not match the module
or when note IDs are missing. Orphaned notes are shown as a warning but do not
block import.

Limitation: it checks only ID presence, not content, duplicates, or cycles.

## Import (`importModuleFromZip`)

```ts
const { module, notes } = remapImportedModule({ module: moduleData, tree, notes: notesData });
// validate module and every note against JSON Schema
// write module, notes, and mention-index records in one transaction
```

Behavior:

- **IDs are regenerated.** `remapImportedModule` creates a new module ID and new
  note IDs, rewrites every `noteTree.noteId`, and sets each note's `moduleId` to
  the new module ID. Importing the same archive twice creates a second copy
  instead of overwriting the first.
- Notes keep their content, type, tags, hidden flag, and original timestamps.
- Module and notes are validated against the JSON Schemas before writing.
- Module, notes, and `indexations_mentions` records are written in a single
  transaction.
- The caller still has to reload the Pinia stores (or the page) to see the new
  data.
- File/asset references are not rewritten (there are none today).

Callers:
- `HomeView.handleModuleImport` imports immediately; validation now happens
  inside the import service.
- `ModulesView.handleModuleImport` (button commented out) parses, validates,
  shows the modal, then imports.

## Export (`ModuleView.handleExportModule`)

- Collects all notes with `moduleId === module.id`, including hidden ones.
- Writes `module.json`, `tree.json`, one file per note, and `summary.json`.
- Uses the module name for the filename, replacing every non-alphanumeric
  character with `_`.

It does not include:
- parties, monsters, encounters, playlists attached to the module,
- bookmarks,
- mention links,
- note types,
- any assets referenced by notes.

## Markdown → ZIP script

`node scripts/markdown-to-json.js --name "Module Name" path/to/file.md`

1. Splits input on ATX headings (`#`..`######`).
2. Cleans section content with `removeMarkdown` + `sanitizeHtml` into plain
   text.
3. Generates a module with `nanoid(10)`.
4. Generates one note per section with `hidden: true`.
5. Builds a tree from heading levels.
6. Writes `output/<sanitized-name>_module.zip`.

### Script behavior

- The Markdown file is optional and defaults to `docs/cos.md`.
- One module ID is generated and shared by `module.json` and every note.
- Note content is preserved as Markdown; only titles/module names are cleaned.
- Remaining limitations:
  - the tree builder only pushes nodes as roots when `level === 1`; a document
    starting at `##` produces an empty tree;
  - duplicate headings create separate notes with the same title;
  - no table of contents, front matter, or metadata mapping is produced.

## Recommended import policy (proposal)

1. Validate module and notes against schemas **before** writing.
2. Generate new IDs for the module and every note, then rewrite `noteTree` and
   note `moduleId` consistently.
3. Rebuild the mention index for imported notes.
4. Write in a single transaction that also updates the Pinia stores.
5. Offer "merge" vs "replace" semantics.
6. Preserve original timestamps or record an `importedAt` field.

See [proposals/technical-proposals.md](../proposals/technical-proposals.md).
